# Durable Desktop cohort execution

`runDesktopCohort` runs a frozen synthetic comparison through `runDesktopFixture` with one shared request budget and one pinned tokenizer worker. It accepts only an explicitly identified isolated replica. It neither discovers credentials/resources nor enables a live-cell experiment.

The caller provides `plan`, a new absolute `outputDirectory`, trusted `prepareCase(entry, {signal})`, `createInputTokenCounter({signal})`, and `fetchImpl`. The optional `systemPrompt` defaults to Desktop's actual prompt; its SHA-256 must match the plan. Both factories must honor cancellation. A late tokenizer factory result is closed after a timeout.

The version-1 plan binds `runId`, `desktopRevision` (40-character Git revision), `protocolSha256`, `fixtureSourceSha256`, `systemPromptSha256`, `tokenizerIdentity`, an `arms` map of names to distinct served-model IDs, `resource` with `mode: isolated-replica`, `instanceId` and exact `origin`, `maxWallMs`, `concurrency` (1 or 2), `requestBudget` and ordered `entries`. Request-budget fields are `maxHttpCalls`, `maxTotalTokens`, `maxInputTokensPerRequest` and `maxConcurrentRequests`.

Each entry specifies `key`, `scenarioId`, `fixtureId`, `arm`, `phase` (`warmup`, `development`, `regression` or `holdout`), `initialInputSha256` and the Desktop fixture `limits`: `maxModelTurns`, `maxToolCalls`, `maxHttpCalls`, `maxWallMs`, `maxCompletionTokens`. Every scenario/phase must include every arm exactly once, with equal initial-input hashes and limits. Phases must progress from warmup through development/regression to holdout. A holdout requires warmups for every arm; all warmups must finish with both successful execution and a passing verifier before a later phase starts. Array order is the dispatch order; a caller can freeze counterbalanced ordering in this manifest. Compute initial-input hashes offline using the actual Desktop compiler: the hash is SHA-256 of Desktop canonical JSON for the final direct-cortex body excluding only `model`. No model response is needed to compile those inputs.

`prepareCase` returns a fresh `{fixture, tools, verify, modelConfig}` for each arm, using isolated synthetic world state. Its configuration must resolve to the explicit replica origin. The cohort enforces direct-cortex, the plan's expected model, prompt and limits; the single-fixture runner supplies both thinking-off fields. Secondary thinking configurations need a separately supported executor/tokenizer recipe. No custom repair/retry loop is added here.

## Durable outcomes and interruption

Exclusive output-directory creation claims the run. Existing directories are always refused, including completed runs, partial startup, concurrent invocation and process death. Use one canonical output path for the pinned run in the cloud launcher; never create another path to replay a consumed holdout or reset its allowance.

The manifest and hash-chained journal are persisted before dispatch. Each HTTP call records the synthetic request body, body hash and shared budget snapshot, and fsyncs its intent before transport. Headers/credentials and query strings are not copied. Results are written atomically before a completion event. Directory entries are synced on POSIX; Windows retains file fsync and atomic rename but cannot make the same power-loss directory-durability claim. Artifacts contain synthetic prompts/answers and belong in the research artifact store, not public PR comments.

A completed execution is not a quality pass. `summary.json` retains every declared entry; unresolved entries remain unknown and an interrupted/limited run is incomplete. Each summary entry exposes `verifiedComplete`, which requires a successful execution and a passing verifier; a standalone verifier verdict cannot erase an execution error. The independent comparison decides quality separately. `missionComparisonEligible` remains false. Unknown usage consumes the full input/output reservation. Identity/input mismatches, aggregate limits, cancellation and replica 5xx stop further admission. The shared budget governs warmup and auxiliary entries as well as scored entries.

The run timer covers tokenizer startup, preparation, dispatch and verification. This process-local timer is not a cloud shutdown mechanism: the serving owner must bind the real instance/image/model identity, maintain cumulative spend across jobs, install an external stop guard, and preserve these files on durable storage. Killing the process leaves the last persisted reservations and a consumed run; it does not authorize a retry or infer whether a remote in-flight request completed. The module does not start/stop instances, train weights, release a model, or certify a supplied resource label against AWS.
